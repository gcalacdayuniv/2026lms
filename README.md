# Working Agreement (read this first)

This section is the standing instruction for every task. Keep it current when a new rule is agreed.

**How to work**
1. Plan briefly, then work in batches that stay within the token limit. Give the output of each batch so progress is not lost.
2. Commit and push finished work straight to `main` of the GitHub repo (no zip needed). Commit only after the tests pass, with a message that says what changed. If a push is refused, say so and send a zip of the changed files instead.
3. Test before delivering: worker changes against a local SQLite D1 test, UI changes in a browser (Playwright). Say what was tested and what was not.

**Delivery (every task)**
- Give full replacement files, never snippets.
- Commit and push the changed files to `main`; the commit includes the README update. Do not send a zip unless a push is not possible.
- Update this README in the same commit so it matches the current setup (add or remove only what changed), including the "Setup & Deploy" notes: required secrets and vars, tables created automatically vs. anything to run manually, deploy steps for the worker and the front end, and any one-time action after an update.

**Code rules**
- Keep existing element IDs. Escape all user text (`escapeHtml` / `safeUrl` in `js/html-utils.js`).
- `SESSION_SECRET` is a Worker secret; `ALLOWED_ORIGIN` is in vars.
- Routes not listed in `auth.js` RULES are lecturer-only, and `courseId` must belong to the signed-in lecturer.
- New D1 tables and columns are created by the worker (`ensure…` functions); no manual database step.
- Mobile first: usable at phone width, tap targets of at least 44px.

**Privacy and data rules**
- See "Lecturer's Notes: Privacy Rules" and "Exams Tied to a Course Title" below.

**Reply style**
- Brief and direct, no recap of steps. End with: what changed, what was tested, what to deploy (worker and/or front end), and one next step if there is one.

**Accessibility (standing rule)**
- The app serves legally blind students. Every new form field needs a visible `<label>` (above the field, `a11y.js` pairs it automatically) or an `aria-label`; icon-only buttons need `aria-label`; errors use `role="alert"`; a button's `aria-label` must start with its visible text. Keep text contrast at 4.5:1 (use the 700 shade for green/teal buttons and gray-500 or darker for small text). Before delivering UI changes, run the axe-core audit (login, register, dashboard, class, scores, exams, summary, exam builder, student exam; light and dark) and keep it at 0 violations.

# Online Portal - System Architecture & Developer Guidelines

## Role & Persona
You are a Senior Full-Stack Developer acting as the primary maintainer for the "Online Portal." You write clean, robust, secure, and scalable code following a Modular Monolith Architecture. You understand how to physically separate concerns by domain while keeping the deployment and execution context unified.

## Repository & Version Control
This project utilizes **GitHub** as its central repository for version control. We use GitHub to manage all source code and leverage it to streamline our automated deployments for both the frontend (Cloudflare Pages) and the backend API (Cloudflare Workers).

## Architecture & Tech Stack
The project relies on a modular monolith stack running entirely on Cloudflare's edge network, integrated with Google Workspace for file storage.

### 1. Frontend (Cloudflare Pages)
The client-side is a static Single-Page Application (SPA) using Vanilla JavaScript, TailwindCSS (built into `tailwind.css`, see "Tailwind build"), and FontAwesome. JavaScript is strictly modularized into native ES Modules residing inside a `js/` directory.

* **`index.html` & `styles.css`:** Main entry point, the static layout shell (viewport uses `viewport-fit=cover` for iPhone safe areas), and custom styles: fade/scale/sheet animations, skeleton shimmer, attendance unsaved-changes indicator, pinned Class Summary columns, and the `dialog-open` scroll lock.
* **`js/globals.js`:** Core configurations (points to the Worker API domain via `CONFIG.API_URL` set to `https://2026-api.plv.workers.dev`), shared state (`AppState`), and a centralized API wrapper (`apiFetch`).
* **`js/components-utils.js`:** Contains shared UI utility functions, such as avatar URL formatting to bypass Google Drive hotlinking blocks.
* **`js/components-auth.js`:** Encapsulates authentication HTML component templates including the Login screen and Registration screen (including `Legally Blind` accessibility tagging).
* **`js/components-dashboard.js`:** Contains UI layouts for the fixed header, responsive profile sidebar (displaying the user's name and username), modals for Update Details, Change Password, Course Creation, Program Management, User Management (full screen on phones), and the Student Document Submission modal (bottom sheet on phones), plus the Submission History, Group Members and Details sheets.
* **`js/components-class.js`:** Manages Class Roster views (with `Legally Blind` accessibility badges and priority sorting), attendance controls (a single **Save All** button; a changed row also autosaves on its own), term settings, the Class Summary (full screen on all devices), Record Scores and Attendance Dates panels (full screen on phones), the Course Actions, Manage Student, Add Student and No Class Days sheets (bottom sheets on phones), performance summaries (with clickable Written, Narrative, Individual, Report, Tasks and Major Exam score cards), student management modals (with disability/eye condition tagging), and the Student Caller (Recitation Picker) modal interface.
* **`js/components-exam.js`:** Encapsulates the UI templates for the Exam Manager (full screen on phones; featuring a plain Create Exam button, the exam list, Bonus Question Manager, and Class Assignment & Schedule Configurator), the Lecturer Full-Screen Presentation Overlay, and the Student Full-Screen Accessible Exam Overlay with high-contrast controls.
* **`js/components.js`:** Acts as a barrel file to export shared utilities and UI components from the domain-specific component modules.
* **`js/router.js`:** Hash-based client-side router (`AppRouter`). Manages view toggling and triggers data loading routines asynchronously, including dynamic route parsing mapping to specific Class IDs.
* **`js/auth.js`:** Handles login (with password visibility toggling), registration (including dynamic program list loading), session management, DOM event delegation, dynamic form masking, user detail updates, password updating logic, interactive panel/modal toggling, global image viewing navigation, and user management status controls.
* **`js/course.js`:** Encapsulates the complete event binding lifecycle for Course Management, serving as the master orchestrator for actions, forms (including document upload processing and dynamic input toggling for files vs. URLs), student disability tag updates, inputs, and routing clicks across modular domain files.
* **`js/course-dashboard.js`:** Manages lecturer and student dashboard rendering views. For students, it automatically queries and renders the **Assigned Accessible Exams** section, complete with a voice read-aloud trigger and direct **Enter Exam** triggers.
* **`js/course-class.js`:** Handles detailed class screen rendering, student sorting algorithms (prioritizing seat numbers and `Legally Blind` accessibility tags), data population for roster elements, print-ready roster exports, and enrollment management overrides. The lecturer's `.view-summary-trigger` click is handled only by the delegated listener in `course.js`; do not bind it again here or the confirmation prompt fires twice.
* **`js/course-scores.js`:** Powers the lecturer's Record Scores modal (create, edit and delete assessments, enter per-student scores with Enter-key navigation) and renders each student's score cards and breakdown popups. Supported categories: Written (Quizzes/Long), Narrative, Individual, Performance (Tasks), Report and Major Exam.
* **`js/course-summary.js`:** Powers the lecturer's Class Summary modal: a searchable class-wide table per term (Mid, Final or both) covering attendance, participation and all assessment categories, with a CSV export. Student summaries are loaded concurrently.
* **`js/course-attendance.js`:** Controls core attendance metrics, term period calculation rules, no-class day mapping, draft caching storage, and batch persistence through **Save All** (`POST /api/attendance`, which replaces the whole day) and the per-row autosave (`POST /api/attendance/single`, which writes only that student's row). Never save one student through the bulk call: it would remove the other students.
* **`js/course-attendance-dates.js`:** Lecturer tool (Course Actions > Attendance Dates) listing every date that has attendance records, with change-date, delete and merge-two-dates actions. Merging adds participation points and keeps the stricter status per student (Absent > Late > Excused > Present).
* **`js/course-recitation.js`:** Manages the Student Caller spinning wheel logic. It features Mode 1 (weighted probability distribution favoring students with minimal scores) and Mode 2 (unique caller ensuring students are not called twice in a single day by caching lists locally).
* **`js/exam-builder-model.js` / `js/exam-builder.js`:** The Exam Builder (full-screen overlay on every device, opened from Manage Exams; questions are added with a purple + button that opens a question-type picker; Template, Import and Export buttons are in its header): a Google-Forms-style Form view and a spreadsheet Grid view editing the same questions (Multiple choice, Multiple answer, True or False, Identification, Numeric, Enumeration, Ordering, Matching, Essay, each with its own points; up to 10 choices or 10 matching pairs; Part numbers start at 1), saving through `/api/exams` and `/api/exams/update`. The model file is pure data code (no DOM): row conversion, validation, CSV reading (`,` `;` or tab, old 6-column, Choice A-H and 0-based Part files still import) and writing. CSV or Excel (.xlsx, first sheet; the SheetJS reader loads from cdnjs only when an Excel file is picked) import (inside the builder) fills the questions so nothing is saved unchecked. When the builder is opened from a class it also shows a Record Scores panel (link and enable, term, category, dates, who can take it) that links the exam to the class on save, the same as Link & Assign Students.
* **`js/course-exam.js`:** Orchestrates the exam list (type chips, points, Edit, Export CSV, Copy), CSV import into the builder, the template download (via the builder), bonus question builder, class-level exam linking with date window scheduling and per-student access checkboxes, the lecturer exam presentation state machine, and the student dashboard **Accessible Exam Overlay** powered by the Web Speech API (`window.speechSynthesis`) with voice confirmation on choice selection, persistent local draft saving, and automatic score recording.
* **`js/omr-sheet.js`:** Layout of the printable bubble answer sheet (a 180 x 240 mm frame with four corner markers, a 6-digit student number grid `00-0000`, and up to 100 questions with 2-5 choices) and `buildSheetHtml()`, which produces the print-ready page for Letter or A4. The sheet shows an optional header (asked when printing, remembered on the device; the assessment name is not printed), one line for Name / Year & Section / Date, the instructions, then four answer columns. The compact student number grid sits at the top of the first column with question 1 right below it, so the page has little blank space. Its numbers are shared with `omr-scan.js`; change both together.

Returns the student number and one answer per question (`BLANK` = -1, `MULTIPLE` = -2), and draws a green/red/blue review overlay.

Only if the sheet cannot be found in the picture is the whole photo shown on top.
* **`js/course-scan-queue.js`:** Device cache (`localStorage` key `omr_pending_v1`) for scanned sheets not yet in the database (answers only, no photos). A sheet enters the cache when it is ready (student matched, not a duplicate on screen) and is deleted only after the server confirms the save, so an offline or closed page loses nothing. Uploads wait 3 seconds after the last edit (20 seconds while a live review is open), retry every 15 seconds (6 attempts, then **Upload now**), and run again when the browser comes back online or the scanner is opened.
* **`js/course-scanner.js`:** Lecturer tool (Course Actions > Scan Answer Sheets). The answer key comes from an exam in Manage Exams (multiple-choice questions only; identification questions are skipped) or is typed in (which also saves the exam in Manage Exams). Photos are read one by one, or with **Live Scan** (the in-dialog camera checks every frame for the four corner squares, shows a green outline and hints such as "Move closer" or "Too dark", and runs full screen and captures by itself once the sheet has been steady for 2 seconds; after one capture the camera closes and that sheet is shown right away in the same full-screen view (student, score, photo overlay, answers) with **Capture again** and **Back to scan menu** at the bottom; the sheet is also added to the review list). Each sheet is matched to a student by the shaded student number (digits only; the lecturer can correct the number, pick the student, or fix a misread answer), and duplicate students block saving. Saving finds or creates the assessment, **merges** with the scores already recorded (`POST /api/assessment-scores` replaces every score of an assessment), asks before replacing a different score, and caps `raw + bonus` at the assessment's Max Score, as the accessible exam does.
* **`js/ui-feedback.js`:** `UI` helper: non-blocking toasts (`UI.success/error/warning/info`) and a promise-based `UI.confirm` modal (`role="alertdialog"`). Use these instead of `alert()` / `confirm()`.
* **`js/skeletons.js`:** Static gray placeholder blocks shown while data loads (screen-reader friendly, contains no user data).
* **`js/date-utils.js`:** Local-timezone date helpers (`getLocalDateString`, `parseLocalDate`, weekday matching). Never use `toISOString()` for calendar dates: it returns the UTC date, which is the previous day in the Philippines before 8:00 AM.
* **`js/a11y.js`:** Dialog accessibility and phone behaviour, driven by the DOM so modals only need to toggle the `hidden` class. It makes everything behind the top dialog `inert`, sets dialog roles and labels, traps Tab, closes on Escape, and restores focus. On phones it also locks page scroll (`html.dialog-open`), lets the browser **Back** button close the top dialog (one history entry per closable dialog), and supports **swipe down** on a bottom sheet's handle or header to close it.
* **`js/app.js`:** The master orchestrator that imports and initializes all modules.

### 2. Backend API (Cloudflare Workers)
* **Worker files:** `worker/worker.js` imports `auth.js`, `password.js`, `scan-grade.js`, `grading.js`, `schema.js`, `attendance.js`, `scores.js`, `exams.js`, `uploads.js`, `accounts.js`, `courses.js`, `scan-sheets.js`, `gas.js`, `shared.js`, `constants.js` and `http.js`, so all of these files must be present when the Worker is deployed (a missing one stops it from starting).
* **Worker split (route files):** `worker.js` now only handles CORS, the sign-in check and the order of the route files; the routes live in `uploads.js` (`handleUploads`: submissions, chunked uploads, grading a submission, plus the upload checks), `accounts.js` (`handleAccounts`: register, login, password, profile details, year-level advance, user list and status), `courses.js` (`handleCourses`: programs, classes, enrollment, rosters, student details, lecturer notes, recitation pool, groups) and `scan-sheets.js` (`handleScanSheets`), next to the earlier `attendance.js`, `scores.js` and `exams.js`. Each has the same shape: `export async function handleX(request, env, path, url, corsHeaders)` returns a Response when it owns the route, otherwise `null`. `gas.js` holds the Apps Script calls (`gasUrl`, `callGas`) used by uploads, scan photos and sign-up avatars; `CLEAR_REACTIVATION_SQL` and `currentTermNow` moved to `shared.js` because accounts and courses both use them. ### 3. Database Layer (Cloudflare D1 - Serverless SQLite)
The database uses Universally Unique Identifiers (UUIDs) for all primary keys, generated on the edge via `crypto.randomUUID()`. 

**Note: Ensure the following tables are created and updated for the system to function correctly:**
* **`Programs`:** Program_ID (UUID), ProgramCode (e.g., BSCS, BSIT).
* **`Users`:** User_ID (UUID), Username, Password, Name, Avatar, Email, Contact_Number, Student_Number, account_status, course, year, section, Program_Course, Program_Year, Program_Section (lecturer-assigned program details, separate from the class `course`/`year`/`section`; added by `migrations/001_program_fields.sql`), eye_condition (`No Eye Condition`, `Near Sighted`, `Far Sighted`, `Legally Blind`), role (Default: 'Student'), registration_timestamp (DATETIME).
* **`Courses`:** Course_ID (UUID), CourseCode, CourseTitle, ScheduleDay, TimePeriod, Lecturer_ID (FK mapped to Users.User_ID), Target_Course, Target_Year, Target_Section, Room, Archived, AcademicYear (e.g. `2026-2027`), Semester (`1st Semester`, `2nd Semester`, `Summer`), Midterm_Start, Midterm_End, Final_Start, Final_End.
* **`Enrollments`:** Enrollment_ID (UUID), Course_ID (FK), Student_ID (FK), Seat_Number, Group_Name, Assigned_Topic.
* **`Course_Sessions`:** Session_ID (UUID), Course_ID (FK), Date (TEXT), Is_No_Class (INTEGER).
* **`Attendance`:** Attendance_ID (UUID), Course_ID (FK mapped to Courses.Course_ID), Student_ID (FK mapped to Users.User_ID), Date, Status (Present, Late, Absent, Excused), Performance_Points (Integer).
* **`Submissions`:** Submission_ID (UUID), Course_ID (FK), Student_ID (FK), Term, Title, Description, Type, File_URL, Timestamp (DATETIME), Grade_Narrative, Grade_Individual, Grade_Report (REAL, nullable).
* **`Assessments`:** Assessment_ID (UUID), Course_ID (FK), Term (`MidTerm` or `FinalTerm`), Category (`Written`, `Narrative`, `Individual`, `Performance`, `Report` or `MajorExam`), Title, Max_Score (REAL), Date (TEXT), Created_At (DATETIME, default `CURRENT_TIMESTAMP`). If the table has a CHECK constraint on `Category`, it must allow all six values.
* **`Assessment_Scores`:** Score_ID (UUID), Assessment_ID (FK), Student_ID (FK), Score (REAL). Scores are validated server-side to be between 0 and the assessment's Max_Score.
* **`Exams`:** Exam_ID (UUID), Lecturer_ID (FK mapped to Users.User_ID), Title (TEXT), ExamData (TEXT, JSON array of `[part, question, choices, answer, explanation, isBonus, type, ordered, meta]`. type is `mc`, `multi`, `tf`, `id`, `num`, `enum`, `order`, `match` or `essay`; rows saved before types existed have only the first six values and the type is worked out from the choices. answer is text, or an array of choice texts (multi), items (enum, order) or `[left, right]` pairs (match). meta is `{points, mode:'all', tol, extra:[]}` and may be missing: points defaults to 1 (enum: item count, match: pair count, essay: 5), `mode:'all'` makes multi/order all-or-nothing, `tol` is the numeric tolerance, `extra` holds wrong matching choices. Partial credit is a share of the points rounded to 2 decimals)), Created_At (DATETIME).
* **`Class_Exams`:** Class_Exam_ID (UUID), Course_ID (FK mapped to Courses.Course_ID), Exam_ID (FK mapped to Exams.Exam_ID), Assessment_ID (FK mapped to Assessments.Assessment_ID), Term (`MidTerm` or `FinalTerm`), Category (`Written`, `Narrative`, `Individual`, `Performance`, `Report` or `MajorExam`), Is_Active (INTEGER, 1 or 0), From_Date (TEXT), To_Date (TEXT), Created_At (DATETIME, default `CURRENT_TIMESTAMP`).
* **`Exam_Assignments`:** Assignment_ID (UUID), Class_Exam_ID (FK mapped to Class_Exams.Class_Exam_ID), Student_ID (FK mapped to Users.User_ID), Is_Enabled (INTEGER, 1 or 0), Status (`Pending` or `Completed`), Raw_Score (REAL), Bonus_Score (REAL), Final_Score (REAL), Max_Score (REAL), Answers_JSON (TEXT), Submitted_At (DATETIME).

## Testing and Deploy Checklist

**Before uploading (on your computer, Node 22 or newer):** `sh tools/tests/run-tests.sh` runs, in order: a syntax check of every JavaScript file, a Worker lint for undefined names (catches a missing import after a file is split), the Worker tests (`tools/tests/worker.test.mjs`: the real Worker code against an in-memory SQLite that behaves like D1: login and lockout, roles and ownership, attendance, scores, exams, sign-up limits; plus a check that every route written in the source still answers, so a route lost in a file split fails the test), and a check that `tailwind.css` is up to date. Add `--phone` to also open the app in a phone-sized Chromium with fake data and the real Content-Security-Policy (`tools/tests/phone-check.cjs`; first time only: `npm i playwright` then `npx playwright install chromium`); it reports policy violations, Tailwind classes missing from `tailwind.css`, sideways scrolling and script errors. When a bug is fixed, add a check for it to `worker.test.mjs`.

**Deploy order:**
1. Upload the whole zip with the folder layout kept (`worker/` files all go together; the Worker will not start with some of them missing).
2. If `tailwind.css` is in the zip, upload it too. After any change to a Tailwind class run `sh tools/build-css.sh` first.
3. Worker: deploy `worker/` (`wrangler deploy`, or the Git integration). `keep_vars = true` keeps the dashboard secrets.
4. Pages deploys the site files (`index.html`, `js/`, `*.css`, `_headers`, `sw.js`). Open the site once and reload so the service worker picks up the new version (cache name in `sw.js`).
5. If `gas/Code.gs` changed, paste it into the Apps Script project and deploy a **new version** of the web app.

**Settings that must exist (Cloudflare dashboard, Worker > Settings > Variables and Secrets):** secrets `SESSION_SECRET` (16+ characters) and `GAS_SECRET` (same value as the `SECRET` script property in Apps Script); variable `ALLOWED_ORIGIN` (your site, comma-separated if several). Optional: `REGISTER_MAX_PER_IP` (sign-up attempts per address per hour, default 60) and `PBKDF2_ITERATIONS` (paid plan).

**Smoke test after every deploy (5 minutes, on a phone):**
1. `./tools/security-check.sh https://<worker-url> https://<your-site>`: all PASS.
2. Sign in as a lecturer: course list appears; open a class; mark one student Present (swipe or tap); reload: the mark is still there.
3. Open Scores, Exams and Class Summary: each opens and shows data. Export the Class Grade (on a phone the Share / Save button appears).
4. Scan one sheet (camera opens, a result appears).
5. Sign in as a student: courses and the exam list show; sign out.
6. Browser console: no "Refused to load" (Content-Security-Policy) and no red errors.

**Rolling back:** the previous Worker version can be restored in the Cloudflare dashboard (Worker > Deployments > Rollback); for the site, redeploy the previous commit in Pages. If only the Content-Security-Policy causes trouble, restore the previous `_headers`. Database changes in this project are additive (lazy `ensure*` functions add tables, columns and indexes), so a rollback does not need a database rollback.

## Environment Variables
We use the following environment variables strictly within the API (`worker/wrangler.toml` and `worker/worker.js`):
* **`ALLOWED_ORIGIN`**: Secures CORS by strictly defining the permitted frontend origin (e.g., `https://plv.workers.dev`).
* **`GAS_WEBHOOK_URL`**: The proxy endpoint used to transmit base64 payloads to Google Apps Script.
* **`SESSION_SECRET`** (Secret, set in the Cloudflare dashboard, never in `wrangler.toml`): signs login tokens; 16+ random characters. `wrangler.toml` has `keep_vars = true`, so a deploy keeps variables and secrets that exist only in the dashboard (without it a deploy can remove dashboard-only plain variables).
* **`PBKDF2_ITERATIONS`** (optional): password hashing rounds, up to 100000 (paid plan).
* **`REGISTER_MAX_PER_IP`** (optional): sign-up attempts allowed per address per hour (default 60; each student number is also limited to 5 per hour).

The bulk call still treats the list as the whole day: students missing from it are removed.
* **Password storage (`worker/password.js`):** passwords are stored as salted PBKDF2-SHA256 (`pbkdf2$rounds$salt$hash`, 10,000 rounds by default so a sign-in stays under the free plan's 10 ms CPU limit; set the variable `PBKDF2_ITERATIONS`, up to 100000, on a paid plan). Older unsalted SHA-256 hashes still sign in and are replaced by a salted hash at that person's next sign-in. Sign-in looks the account up by identifier and then verifies the password; never compare a hash in SQL.
* **Server-side authorization (`worker/auth.js`):** `POST /api/login` returns a signed token (HMAC-SHA256, 7 days) that `apiFetch` sends as `Authorization: Bearer ...`. Every `/api` request passes one gate: it checks the token, reads the user's role and `account_status` from `Users` (so a suspended account or changed role works at once), applies the route's rule from `RULES` (`public`, `any` signed-in, or `lecturer`; a route that is not listed is lecturer-only), makes students use only their own ids (`self` / `mine` fields) and enrolled courses, and makes a lecturer touch only their own courses, assessments, exams, class exams, submissions and scan sheets. The gate stays **off** until the Worker secret `SESSION_SECRET` (16+ random characters) is set: `wrangler secret put SESSION_SECRET`, or Cloudflare dashboard > Worker > Settings > Variables and Secrets. Do not put it in `wrangler.toml`. After it is set, anyone signed in from before must sign in again. New routes must be added to `RULES` in `worker/auth.js`.
* **Exam date windows and participation points:** a class exam's From/To dates (date only) are compared with today's date in the visitor's timezone (default Asia/Manila), not UTC, so an exam opens at local midnight and closes at the end of the last local day (`isWithinScheduleWindow`). `POST /api/add-participation-points` adds points in a single SQL statement, so two quick taps no longer overwrite each other.
* **Class summary in one call and database indexes:** `GET /api/class-summary?courseId=` (lecturer, own course) returns the course terms, no-class sessions, and each enrolled student's attendance records and assessment scores in five queries; `js/course-summary.js` uses it and falls back to one `/api/student-summary` call per student if the Worker does not have it yet. The Worker also creates plain indexes on Attendance, Enrollments, Assessments, Assessment_Scores, Submissions, Course_Sessions and Courses, and four on Users (username, email, phone, student number, so sign-in is an index lookup instead of a table scan) on first request (`ensureCoreIndexes`; a missing table is skipped and retried at the next Worker start).
* **Sign out after a password change:** `POST /api/change-password` and `POST /api/reset-student-password` set `Users.Password_Changed_At` (column added automatically), and the gate rejects any token issued before it ("Your password was changed. Please sign in again."). Changing your own password returns a fresh token that `js/auth.js` stores, so only your other devices are signed out. A reset signs the student out everywhere.
* **Class Grade export (`js/class-grade-export.js`, `js/class-grade-template.js`):** Class Summary has a **Class Grade (.xlsx)** button that downloads the lecturer's CLASS GRADE workbook (Midterm, Final Term and Summary blocks, same look and formulas). The template is stored as base64 in `class-grade-template.js` (the front end can only deploy `.html`, `.css`, `.js`); to change the layout, replace that string. ExcelJS 4.4.0 is loaded from jsDelivr (cdnjs as fallback) only when the button is used. Students are listed A-Z; a student who is not Active gets the status in Remarks. Per term: Written, Narrative and Individual assessments fill the 9 written-output slots, the performance block starts with **Attendance** and **Participation**, then Performance and Report fill the remaining slots (date order, labels = titles, perfect score = Max Score), and Major Exam scores are added into the exam column.
