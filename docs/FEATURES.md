## Recent Feature & Security Updates
* **Student course summary header:** the small heading is the course code (instead of "My Course Summary") with the title under it. Seat, Group and Topic sit on one line, each label above its value; a long group name or topic slides back and forth so it can be read in full (the topic pop-up is gone; the group still opens its members list). Submission History is a full-screen page on phones like Submit Document (`js/components-dashboard.js`, `js/course.js`, `js/student-summary-ui.js`, `styles.css`).
* **Class screen header:** the "Class Roster & Attendance" heading is gone; the schedule day and time, room, target audience badge and the edit (pencil) button now sit at the right of the blue header bar (`js/components-class.js`; the button keeps id `editRoomBtn`).
* **Student list sorting:** the class roster (attendance tab) and the Add Student list have a sort drop-down: Default order (as before), Name (A-Z) or Student number (numbers compared as numbers, blanks last). The choice is kept on the device (`localStorage` key `student_sort`). Sorting only moves rows; saving and filtering are unaffected (`js/course-roster-tools.js`, `js/components-class.js`, `js/course-class.js`, `js/course.js`).
* **Attendance unsaved indicator:** the orange dot on Save All and the "Unsaved changes" label are hidden unless the date on screen has unsaved changes or this device keeps a draft for another date; they used to show all the time (`js/course-attendance.js`, `js/components-class.js`).
* **Password reset:** `POST /api/reset-student-password` only resets a student account (never a lecturer's) to a random 10-character temporary password, returned once and shown to the lecturer; it is no longer `123456`. API responses also carry `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.
* **HTML escaping:** every `innerHTML` template was audited. The remaining unescaped values (error messages shown in lists, roster print table cells and title, program line, program drop-down, score cells, linked-exam dates) now use `escapeHtml()`; the rest were already escaped.
* **Attendance writes:** `POST /api/attendance` and `/api/attendance/single` update each student's row or add it (`upsertAttendance`), in one database transaction, so a failed save leaves the day unchanged and existing rows keep their ids. The bulk call still treats the list as the whole day: students missing from it are removed.
* **Password storage (`worker/password.js`):** passwords are stored as salted PBKDF2-SHA256 (`pbkdf2$rounds$salt$hash`, 10,000 rounds by default so a sign-in stays under the free plan's 10 ms CPU limit; set the variable `PBKDF2_ITERATIONS`, up to 100000, on a paid plan). Older unsalted SHA-256 hashes still sign in and are replaced by a salted hash at that person's next sign-in. Sign-in looks the account up by identifier and then verifies the password; never compare a hash in SQL.
* **Server-side authorization (`worker/auth.js`):** `POST /api/login` returns a signed token (HMAC-SHA256, 7 days) that `apiFetch` sends as `Authorization: Bearer ...`. Every `/api` request passes one gate: it checks the token, reads the user's role and `account_status` from `Users` (so a suspended account or changed role works at once), applies the route's rule from `RULES` (`public`, `any` signed-in, or `lecturer`; a route that is not listed is lecturer-only), makes students use only their own ids (`self` / `mine` fields) and enrolled courses, and makes a lecturer touch only their own courses, assessments, exams, class exams, submissions and scan sheets. The gate stays **off** until the Worker secret `SESSION_SECRET` (16+ random characters) is set: `wrangler secret put SESSION_SECRET`, or Cloudflare dashboard > Worker > Settings > Variables and Secrets. Do not put it in `wrangler.toml`. After it is set, anyone signed in from before must sign in again. New routes must be added to `RULES` in `worker/auth.js`.
* **Exam date windows and participation points:** a class exam's From/To dates (date only) are compared with today's date in the visitor's timezone (default Asia/Manila), not UTC, so an exam opens at local midnight and closes at the end of the last local day (`isWithinScheduleWindow`). `POST /api/add-participation-points` adds points in a single SQL statement, so two quick taps no longer overwrite each other.
* **Class summary in one call and database indexes:** `GET /api/class-summary?courseId=` (lecturer, own course) returns the course terms, no-class sessions, and each enrolled student's attendance records and assessment scores in five queries; `js/course-summary.js` uses it and falls back to one `/api/student-summary` call per student if the Worker does not have it yet. The Worker also creates plain indexes on Attendance, Enrollments, Assessments, Assessment_Scores, Submissions, Course_Sessions and Courses, and four on Users (username, email, phone, student number, so sign-in is an index lookup instead of a table scan) on first request (`ensureCoreIndexes`; a missing table is skipped and retried at the next Worker start).
* **Sign out after a password change:** `POST /api/change-password` and `POST /api/reset-student-password` set `Users.Password_Changed_At` (column added automatically), and the gate rejects any token issued before it ("Your password was changed. Please sign in again."). Changing your own password returns a fresh token that `js/auth.js` stores, so only your other devices are signed out. A reset signs the student out everywhere.
* **Class Grade export (`js/class-grade-export.js`, `js/class-grade-template.js`):** Class Summary has a **Class Grade (.xlsx)** button that downloads the lecturer's CLASS GRADE workbook (Midterm, Final Term and Summary blocks, same look and formulas). The template is stored as base64 in `class-grade-template.js` (the front end can only deploy `.html`, `.css`, `.js`); to change the layout, replace that string. ExcelJS 4.4.0 is loaded from jsDelivr (cdnjs as fallback) only when the button is used. Students are listed A-Z; a student who is not Active gets the status in Remarks. Per term: Written, Narrative and Individual assessments fill the 9 written-output slots, the performance block starts with **Attendance** and **Participation**, then Performance and Report fill the remaining slots (date order, labels = titles, perfect score = 100: every output is converted to a base of 100, see Grade base 100), and Major Exam scores are added into the exam column. Attendance = present + half of late + excused, out of the term's class days (excused count as attended); Participation = total points, worth at least 1 point per class day (perfect score = the term's class days, raised to the highest points earned if a student has more; editable in row 5). A term without class days (no term dates) leaves both slots out with a warning. If a block has more outputs than slots (9 written; 9 performance minus the two above), the extras are left out and a warning toast lists them. Ratings, 30/30/40 weights, term grades and the final grade are the template's own formulas, recalculated when the file opens.
* **`worker/schema.js`:** every table, column and index the Worker creates for itself (`ensureScanTables`, `ensureLoginTable`, `ensureAccessibleExamTables`, `ensureManualMarksColumn`, `ensureYearAdvanceTables`, `ensureLecturerNotes`, `ensureReactivationColumns`, `ensureCoreIndexes`, `ensureCourseRoom`, plus the `EXTRA_COLUMNS` list). `worker.js` imports and calls them; add any new self-created table or column here, not in `worker.js`. Moved without changing the SQL.
* **Sign-up limit:** `POST /api/register` counts every attempt (successful or not) per address (`reg:ip:`, default 60 per hour, change with the optional variable `REGISTER_MAX_PER_IP`) and per student number (`reg:sn:`, 5 per hour) in the `Login_Attempts` table, using the same helpers as the login lockout (`loginLockedFor` / `loginFailed` now take a window). Over the limit it returns 429 with "Too many sign-up attempts". The Worker also rejects a password outside 6 to 200 characters, overlong text fields, and a profile photo over about 6 MB; the sign-up form now shrinks the photo to 1024 px JPEG (about 150 KB) before sending (`AuthModule.photoToBase64`).
* **Security hardening:** (1) the Apps Script web address was reachable by anyone who knew it (it is in this public repo) and could write to and read from the Drive folder, including saved answer sheets. Set a `GAS_SECRET` Secret in the Worker and the same value as a `SECRET` script property in the Apps Script project (Project Settings > Script properties), then deploy a new version of the web app: the Worker sends it as `?key=` and `gas/Code.gs` refuses requests without it (until the property is set, both sides keep working as before). (2) The catch-all error handler no longer sends internal error text (table and column names) to the browser; details go to the Worker log. (3) `_headers` adds `X-Content-Type-Options`, `frame-ancestors 'self'` / `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` (camera for the scanner only) and HSTS on Cloudflare Pages. No full Content-Security-Policy yet: Tailwind's CDN script needs inline styles and scripts, so a strict one needs the Tailwind build step first.
* **Shared helpers:** every file uses `escapeHtml` from `js/html-utils.js` (five files each had their own weaker `esc` that missed `'` and backticks; they now import it as `esc`). `js/download-utils.js` holds the one `csvCell` (formula-safe, always quoted), `downloadBlob` and `downloadCsv` (adds the byte-order mark), used by Class Summary CSV, Class Grade export, exam results CSV and the Exam Builder export/template. New code must import these instead of copying them.
* **Cleanup:** the unused `localStorage` key `user` is no longer written (the app reads `portal_user`; logout still removes any old `user` copy), and a stray comment was removed from the end of `worker/worker.js`.
* **CORS:** the Worker never falls back to `*`; an unknown origin gets the primary allowed origin (`ALLOWED_ORIGIN`, comma-separated list allowed).
* **Network handling:** `apiFetch` has a 30 s timeout, retries a failed read once, and shows offline / unreachable messages.
* **Scan Answer Sheets (OMR):** Lecturers can print a bubble answer sheet, have students shade it, then scan the sheets (live camera with automatic capture, the phone camera, or photos from the library) to record scores automatically. The student shades their number (00-0000), the system finds the matching student, shows the score with a photo overlay for checking, and saves to the assessment in Record Scores. It uses `/api/exams`, `/api/assessments`, `/api/class-exams` and `/api/course-details`, and saves through the scan endpoints below (the Worker must be redeployed). Saved sheets (the scanned answers) are stored for later review and manual correction (tab **Saved Scans**). Accuracy depends on a flat, well-lit photo showing all four corner squares.
  * New D1 tables, created automatically by the Worker on first use (`ensureScanTables`): `Scan_Sessions` (one per assessment: key, bonus flags, size) and `Scan_Sheets` (per student: `Original_Answers`, `Answers`, `Score`, `Edited`).
  * `GET /api/scan-sheets/photo?sheetId=` returns one saved photo as base64 (read from Drive through the Apps Script `read` action, so **`gas/Code.gs` must be redeployed**). `Scan_Sheets.Photo_Layout` is `rect1` for straightened photos (added automatically). `Scan_Sheets.Photo_File_ID` holds the Google Drive file id of the sheet's photo (Drive path `Scan Sheets/<course>/<session>/scan_<sheet>.jpg`, uploaded through the Apps Script web app). Re-saving the same capture keeps its photo; a different capture replacing the sheet clears it. The Drive folder must be viewable by lecturers (same requirement as profile photos) for the viewer to load the thumbnail.
  * Duplicate protection: one saved sheet per student per assessment. Each captured sheet has a `scanId` (stored in `Scan_Sheets.Scan_ID`, column added automatically). `POST /api/scan-sheets/save` answers per sheet: written (new student, same `scanId` re-sent, or `replace: true`), `unchanged` (a saved sheet with identical answers), or a `conflicts` entry (different answers, nothing written) that the app shows as **Replace the saved sheet** / **Keep saved, discard this**. `removals: [{studentId, scanId}]` undoes an upload when the sheet is later assigned to another student. The app also flags two sheets for the same student on screen and holds both back.
  * New endpoints: `GET /api/scan-sessions?courseId=`, `GET /api/scan-sheets?sessionId=`, `POST /api/scan-sheets/save`, `POST /api/scan-sheets/correct`, `DELETE /api/scan-sessions` (removes stored sheets only; recorded scores stay). Deleting an assessment also deletes its saved scans.
* **Student Dashboard Accessible Exam Portal & Read-Aloud Engine:** Students automatically see their **Assigned Accessible Exams** directly on their dashboard after logging in. Powered by the native Web Speech API (`window.speechSynthesis`), it tracks local storage drafts and reads aloud assigned exams, questions, bonus indicators, and choices. It features **strict Tab/Shift+Tab focus-trapping**, specific audio instructions when focusing on buttons, and a **double-press `Enter`/`Space` safety mechanism** to lock answers, navigate between questions, and submit exams. Supports keyboard shortcuts (`1-9`, `A-D`, Arrow keys, `R`, `Q`, `Enter`, `Space`, `Tab`).
* **Downloadable CSV Exam Template & Format Guide:** Lecturers can click **Template** in the Exam Builder header to download a sample `.csv` formatted for Excel or Google Sheets.
* **Class Exam Linking, Date Window Scheduling & Per-Student Access Control:** Lecturers can link any exam from the global `Exams` table to a specific class (`Class_Exams`), configure `From Date` and `To Date` schedules to automatically open and close the exam for that class, and toggle checkboxes (`Exam_Assignments`) to enable or disable the exam for individual students (with a quick-select filter for `Legally Blind` students and an explicit "Re-open Exam (Reset)" control).
* **Auto-Recording Exam Scores & Capped Bonus Questions:** Lecturers can append bonus questions or mark existing questions as bonus inside Manage Exams (`POST /api/exams/update` or via CSV column 6). Upon student exam submission (`POST /api/submit-accessible-exam`), the edge worker calculates `finalScore = Math.min(maxScore, rawScore + bonusScore)` so that the total score never exceeds the maximum score, and automatically records the grade into `Assessment_Scores` under the linked assessment name in Record Scores.
* **Student Disability Tagging (`Legally Blind`):** Instructors can tag or update a student's disability status (`Legally Blind`) from the Class Roster's Manage Student modal (`POST /api/update-student-info`), and students can select it during registration. Students tagged as `Legally Blind` display a distinct accessibility badge and are prioritized in roster and summary sorting.

* **Class Summary & Record Scores:** Added a Class Summary modal (searchable, term-filtered table with CSV export that neutralizes spreadsheet formula injection) and a Record Scores modal to the course menu.

* **Phone dialog layouts:** Large panels are full screen and short actions are bottom sheets on phones (see Dialog Layout Conventions). Back closes the top dialog, swipe down closes a sheet, page scroll is locked behind dialogs, and sheets respect the iPhone safe area.

## Scanner: layout is read from the photo, regression check
- **Cause of "exam set and student number are not read":** the student number grid, the SET row and the first answer column sit lower on a sheet printed with sets than on one printed without (`omr-sheet.js` `geoOf`). The set count the scanner assumed is saved per device (`getSetCount`), so a sheet printed on one device and scanned on another, or printed with a different number of sets, was read at the wrong place: the student number came out wrong or with `?`, the SET circle blank, while most other answers still looked fine.
- **Fix (`js/omr-scan.js`):** `detectGeo` checks the 60 printed rings of the student grid at the assumed layout; when they are not there (score under 0.85) and the other layout fits clearly better, it reads that layout instead (`result.layoutChanged`, `result.geo`). `countSetCircles` counts the SET circles actually printed (`result.setsPrinted`). The review and the overlay use the layout that was read. A matching sheet is read as before.
- **Sets guard (`js/course-scanner.js` `rowFromResult`):** a sheet with more SET circles than Exam sets in the Scan setup is not graded (it would use a missing key); the row says to choose that number in Exam sets and scan again.
- **Check:** `node tools/tests/omr-check.cjs` prints real sheets (`buildSheetHtml`), shades 12-3456, a SET circle and answers, makes a perspective "photo" with uneven light and noise, and reads it with the real scanner, for matched and mismatched set counts (plain and mixed sheets, two tilts). `sh tools/tests/run-tests.sh --omr` runs it with the other checks.

## Terms and Conditions, and the camera notice
- **`terms.html`:** plain static page (light and dark) with the terms of use. Clause 4 covers the camera during examinations: photographs for exam integrity, who sees them, how long they are kept. It deliberately does not state how often photos are taken, so the interval can change per exam or per risk without changing the terms. Cached by `sw.js` (`SHELL`).
- **Checkbox:** the sign-in and registration forms have a required "I have read and agree to the Terms and Conditions" box linking to `terms.html`. `js/terms-consent.js` remembers the tick on the device under `terms_agreed_v1`; raise the number in `TERMS_KEY` when the terms change in an important way and everyone is asked again. The check is in the browser only (not stored on the server).
- **Start exam and face verification (`js/exam-secure.js`):** the exam notice has one **Start exam** button (no interval, no "allow camera" wording). A device that already allowed the camera (permission API, or the `exam_camera_ok` flag where Safari cannot query it) goes straight into the exam. Otherwise a full-screen **Face verification** step opens: **Allow camera**, a live preview with an oval, **Take photo**, a check, then the exam starts. The check looks inside the oval for a dark, bright or blank picture and, where the browser has `FaceDetector` (Chrome on Android), for exactly one face in the oval; it is not face recognition and iOS Safari only gets the light check. A failed check shows what to fix and **Retake photo**. Cancel returns to the exam list.

## Admin role and who sees exam photos
- **Admin:** the first Admin is set by hand in D1: `UPDATE Users SET role = 'Admin' WHERE Username = '...'`. After that, an Admin changes any user's role in **Admin tools > Manage Users** (a **Role** dropdown on each card: Student, Lecturer, Admin; `POST /api/update-user-role`, `handleRoles` in `worker/roles.js`). Rules: Admins only (403 otherwise); you cannot change your own role (so there is always an Admin); a lecturer who still owns classes cannot become a student. The person sees the new role after signing in again (the server applies it at once). The card's existing role badge shows the role. An Admin is a lecturer with extra access (`worker/roles.js`: `isLecturerRole` accepts `lecturer` and `Admin`, `isAdminRole`). Sign-in returns `role: 'Lecturer'` plus `isAdmin: true`, so the front end treats an Admin as a lecturer; the profile shows "Admin". The role is read from the database on every request, so a change applies at once. An Admin's own classes work like any lecturer's.
- **Manage Users filters:** four dropdowns under the search box: role (Students, Lecturers, and Admins for Admins only), program course, year and section. The course/year/section choices come from the users on the list; they combine with the status chips and the search box. They reset when the page closes.
- **Stale sessions:** the role is saved on the device at sign-in, so `js/session-role.js` asks `GET /api/me` once at app start and reloads if the role or the Admin flag changed (this is also why a role set in D1 or by an Admin shows up without signing in again).
- **Exam photos:** the initial photo (`Kind 'start'`, the face verification photo when the student went through verification, else one taken when the exam starts) is the only photo a lecturer gets, one picture per student with no gallery: Results shows a **Face photo** button per student and Manage Student > **Review exam photos** shows one picture per exam (`ExamPhotoReview.renderInitial`). The server returns `limited: true` and only `start` photos; fetching a periodic photo (`Kind 'check'`) by id returns 403 for a lecturer. Admins get the full gallery (Results > **All photos**, per-student Photos (n), Manage Student).
- **Admin tools > Exam Photos (Admins only, `#openAdminPhotosBtn`):** every class with photos from all lecturers (search by class or lecturer), then the class's exams, then the full gallery. Routes: `GET /api/admin-exam-photos` (classes) and `?courseId=` (exams); the handler refuses a lecturer with 403. `GET /api/exam-photos` has `adminAny` in `worker/auth.js` RULES, so an Admin skips the class-owner check on it; lecturers keep it.
- **Face verification photo:** kept in `ExamSecure.verifyShot` and sent as the `start` photo when the exam begins (`ExamSecure.initialPhoto`).

## Speed and Connection
- **Instant open:** the dashboard (existing) and now the class screen keep a saved copy in `localStorage` (`dash_cache:` and `class_cache:` keys). Opening paints the saved copy at once, then fetches fresh data. If nothing changed the screen is left alone. If something changed, the screen is redrawn only when no page or dialog is open and attendance has no unsaved changes; otherwise a toast says "Class was updated. Pull down to refresh." Refreshes after an action (`skipSpinner`) never use the saved copy. Both kinds of saved copy are removed on logout (`clearClassCache`).
- **Offline pill:** `app-feel.js` shows a pill at the top while the device is offline and a green "Back online" for 2 seconds afterwards.
- **Route slide (phones):** `router.js` sets `#app-root[data-route]` for dashboard to class (forward) and class to dashboard (back). Only `opacity` and `left` of `<main>` animate, because a `transform` would re-anchor fixed bars and pages. The attribute is cleared after the first draw.

## Accessibility and sign-in cleanup
- **Screen reader / keyboard audit (axe-core, 9 screens, light and dark): 0 violations.** Fixed: login/register fields without names (`A11y.linkLabels` in `js/a11y.js`; it pairs a `<label>` with the field that follows it, also for screens drawn later), password show/hide button now named and `aria-pressed`, `<main>` and `<h1>` on login/register, error and success messages announced (`role=alert` / `status`), Archive/Copy button names now start with their visible text, and contrast (green/teal buttons use the 700 shade, small gray text is gray-500, dark-mode exam highlight text).

## Exam open and close times (GMT+8)

## Exam question types and essay grading

* **`worker/grading.js`:** all grading and the student payload (answers are never sent to students; matching and ordering items are shuffled with a fixed seed). `worker/worker.js` imports it, so deploy both files.
* **Essays** are scored by hand: Manage Exams > Grade Essays (shown for exams linked to the class that contain essays). ## Exam time limit and results

* **Time limit:** set in minutes (empty = no limit) in Link & Assign Students or in the builder's Record Scores panel; stored in `Class_Exams.Time_Limit`. When a student opens a timed exam, `POST /api/start-accessible-exam` records `Exam_Assignments.Started_At` once, so the clock keeps running if the page is closed. The countdown turns amber at 5 minutes and red at 1 minute, announces 10 min, 5 min, 1 min, 30 s and 10 s to screen readers and read-aloud users, and submits automatically at zero. The worker still accepts a submission up to 2 minutes after the limit (`GRACE_SECONDS`) and rejects later ones; Re-open (Reset) clears the start time.
* **Results:** Manage Exams > Results (for exams linked to the class) shows the class summary, score spread, an analysis of every question (average, share fully right, answer counts per choice, common wrong answers, per-pair and per-position results, essay marking progress; "Hardest first" or exam order) and a student list with CSV export. Data comes from `GET /api/exam-results?classExamId=` (lecturer only; analysis in `worker/grading.js`).
* **D1:** `Class_Exams.Time_Limit` and `Exam_Assignments.Started_At` are added automatically the first time the exam tables are used. No manual change.

## Invite codes: expiry, activation, sharing, and automatic deactivation
- **7-day expiry:** a code works for 7 days (`Courses.Invite_Expires`, UTC; shown in GMT+8). After that it is refused ("code has expired") until the lecturer presses **New code**, which gives a different code and a fresh 7 days. Codes that existed before this change got 7 days from the first time the worker ran.
- **Register with a code:** the sign-up form has an optional **Class code**. A valid code makes the account **Active** and enrols the student in that class at once (`invite_code` on `POST /api/register`). A wrong or expired code stops the sign-up before anything is saved. Without a code the account is Inactive (pending) as before.
- **Activate with a code:** a student whose account is Inactive (new, or deactivated) signs in with the class code in the sign-in form (`inviteCode` on `POST /api/login`; the box appears when the server answers `codeActivation: true`). A valid code sets the account Active, clears any year-advance reactivation, and enrols the student. Suspended, Dropped, UD and Graduated accounts are **not** activated by a code, and the password is always checked first.
- **Share:** class menu > Invite Code shows the code, when it expires (GMT+8), and an editable message (how to register, how to activate, when it expires) with **Share** (phone share sheet, else copy), **Copy message** and **Copy code**.
- **Automatic deactivation:** a student becomes **Inactive** when every class they are in is archived, or ended. A class has ended 14 days after the **last day of its term**, which an admin sets in Admin tools > Academic Term > "Last day of this term (end of Finals)" (stored per term in `App_Settings` `term_ends`). With no last day set for a term, its classes never count as ended. Students with no class are left alone; classes with no academic year/semester only count when archived. Code: `worker/term-sweep.js`; runs when a class is archived and on about 1 request in 20 (at most every 6 hours, `last_end_sweep`).
- Un-archiving a class does not re-activate students who were deactivated; they use the class code (or a lecturer sets them Active).

## Secure exam mode (camera photos and leave-to-submit)

Applies to **every online exam** a student takes (`js/exam-secure.js`, `worker/exam-photos.js`).
- **Before starting:** a notice explains the rules and asks for the camera. Without the camera the exam does not start.
- **Photos:** one when the exam starts and one every 30 seconds (320 px JPEG, `POST /api/exam-photo`). They are stored in Google Drive through the Apps Script (`Exam Photos / <classExamId> / <studentId>`); only a reference is kept in D1 (`Exam_Photos`, created automatically). No Apps Script change is needed. A red "CAMERA ON" badge shows while it runs.
- **Leaving the exam:** switching tab, app or window or locking the screen starts a **5 second grace period** (red countdown banner; `AWAY_GRACE_SECONDS` in `js/exam-secure.js` and `worker/exam-session.js`, keep them equal). Back in time = the exam carries on. Phones freeze the page in the background, so the **server enforces it**: the app tells `POST /api/exam-away`, and an attempt away longer than the grace is submitted from its saved answers the next time the student, or the lecturer opening Results, asks (`sweepAway`). Reason shown to the lecturer: "Away too long". The camera turning off while the exam is on screen still submits at once; after a background trip the app restarts the camera and submits only if that fails. The app's own confirm / alert dialogs do not count.
- **Who is exempt:** students tagged **Legally Blind** (screen readers and read-aloud use trigger focus changes). Admin tools > Manage Users > Edit details > **Secure exam mode** can set Default / Always on / Always off per student (`Users.Exam_Secure`, added automatically). The server tells the app per student (`student.secure`), and refuses photos for exempt students.
- **Lecturer view (photo review, `js/exam-photo-review.js`):** two ways to review capture photos by hand. **By exam:** Manage Exams > Results > **All photos** (or a student's **Photos (n)**, which opens that student already expanded); students are collapsible groups with their photo counts. **By student:** Manage Student > **Review exam photos** lists that student's photos across the class's exams, grouped by exam. Tap a picture to enlarge it; Previous / Next, swipe or the arrow keys move through every photo in the list (Esc closes). Pictures load from Drive 3 at a time and only for groups that are open, and are cached while the dialog is open. API: `GET /api/exam-photos?classExamId=` (by exam), `?courseId=&studentId=` (by student, owner checked by courseId), `?photoId=` (one picture); all lecturer-only. Results still show "Left the exam screen: auto-submitted" for auto-submits.
- **Privacy:** photos are used only to check an exam attempt. Delete the Drive folder `Exam Photos / <classExamId>` when the exam is no longer in dispute. Tell students about the camera in the course orientation.
- **Limits:** the browser cannot stop a student using a second device, and a phone call or system alert can end an exam, so tell students to use Do Not Disturb. The photo check is client-side; the server only accepts photos for secure students while the exam is in progress (max 400 per attempt).
